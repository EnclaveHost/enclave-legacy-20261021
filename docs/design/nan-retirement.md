# Nan retirement — implementation and cutover gates

Censorship resistance to external parties and infrastructure failure is the acceptance criterion. Moving every service to one replacement server is insufficient. Preserve platform administration and moderation, host-wallet local restrictions, and private computation. Application TLS remains inside the guest.

**Contract scope correction, 2026-10-20:** reuse the deployed contracts by default.
The on-chain address book is not a Nan dependency; preserve administrator-directed
version changes. Historical fixed-binding session/custody proposals below are
not required production cutovers. Ledger revision 17 is separate lease-race
hardening, not a prerequisite for retiring Nan. Existing sessions, funds and
custody must remain compatible. See `decentralized-architecture.md`, “Existing
contracts first”, for the current acceptance rules.

### Static-site routing correction, 2026-10-19

The initial static-front migration omitted the IPFS `_redirects` rules. Direct
loads of `/dashboard` and other extensionless pages returned the branded 404 even
though their `.html` documents were present. Checking only `/index.html` missed
this regression. All four regions now apply rules generated by
`node scripts/network/site-pretty-routes.mjs PATH_TO_BUILT_SITE/_redirects` inside
the site's main Caddy `handle`, after `root` and before `file_server`. Keep the
existing `handle_errors` for real 404s. Generate from the exact published site,
validate with the service's actual Caddy executable, and reload one region at a
time. Preserve existing-file precedence, nested pages, redirects and query strings.

Verification covered every redirect-file route and a genuinely missing path in
each region: 80 checks passed, including exact published-file hashes and query
preservation. The user's existing signed-in browser showed the restored dashboard,
three hosts and the deployment counts. Future static-front releases must include
this route matrix; a successful root-page request is insufficient.

Its API/control writers and indexd/PostgreSQL writers were already stopped and fenced. Pinning, cleanup, native-certificate and IPNS timers are disabled. ## Host ownership and custody deployment status

`EnclaveHostOwnership.sol` pins a registry and establishes wallet ownership through two-party consent: the registered operator nominates the initial owner and that wallet accepts. Existing ownership can only be transferred by the old owner nominating and the new owner accepting. This ownership contract controls local host permissions; it does not replace platform governance. Payout declarations never confer policy authority.

A host owner commits a local admission document with `setPolicy`. The document binds chain ID, ownership contract and host ID, and carries deployment/app-reference denials and an optional stricter approval requirement for private development. Platform moderation is always enforced. A fresh agreeing chain quorum identifies the current commitment; a missing or mismatching nonempty document fails closed for that host. Transferring ownership clears the former owner's policy. Catalog rejection, delisting and publisher yanks remain mandatory platform refusals.

The custody combiner now accepts a sufficient independent quorum when Enclave answers challenges but refuses or supplies invalid shares. Thresholds, share checks and duplicate-seat exclusion remain intact. The live committee still consists of a single Enclave seat, so source changes alone cannot create independent recovery.

The proposed vault now pins `EnclaveHostOwnership` and its registry at construction. Custodian admission computes the Enclave seat from accepted ownership, never payout declarations. The image builder requires an explicit `--host-ownership` pin. Its membership reader checks fresh agreeing chain state, checks that the vault matches that measured pin, and refuses legacy vaults without that authority interface. This is a new contract/runtime deployment, not an in-place update: leave existing committees on their compatible runtime until a controlled bundle/committee migration is ready. Existing committee flags remain epoch snapshots; ownership changes affect new admissions/handovers.

Do not deploy this custody change as a completed veto migration. Host ownership is now published and bound on nucbox-k11-4. Remaining custody work includes compatible signed/measured runtime releases, activating the wallet-based custody classification, and redistribution into an independently operated committee. Frontend/CLI explicit release selection must enforce platform moderation alongside host-owner restrictions. Other serving paths still require review; existing production runtimes retain their old gates until explicitly activated.

### Host runtime integration (activated on nucbox-k11-4; other hosts require separate activation)

Windows host claims, scans, forced launches and live renewal ticks now consult the host's wallet policy when explicitly configured. A refusal stops the local app before releasing its lease; it does not mark the deployment globally forbidden or permanently prevent a later retry. Linux supervisor claim/version/config gates, live audits and renewals use the same authority; its unconditional yank sweep is disabled in this mode. Resource, tenant consent, placement, isolation, publisher-fee and lease checks remain.

Activation requires `ENCLAVE_CONTRACT_PINS_FILE` plus all four settings: `ENCLAVE_HOST_OWNERSHIP`, `ENCLAVE_HOST_REGISTRY_PIN`, `ENCLAVE_HOST_CATALOG_PIN`, and `ENCLAVE_HOST_POLICY_DIR`. The directory contains public `<policyHash>.json` documents. Policy and catalog pins are read from configuration, never the mutable book. The ownership contract's registry must match the configured pin. Two independently configured RPCs must agree at a recent block; accepted wallet-policy snapshots are reused for at most 15 seconds and cannot outlive the 90-second chain freshness window. Missing ownership, unavailable quorum, unavailable committed documents and mismatches refuse locally. A zero commitment means no additional host-owner deny entries. Catalog rejection, delisting and publisher yanks remain mandatory. Pending versions are allowed only through the private development path unless the host owner requires approval there too.

This mode requires an exact on-chain deployment ID: the supervisor's legacy direct, non-ledger creation API cannot satisfy wallet policy and refuses. The new contract pin file fixes the ledger, registry, catalog and proof bindings at process start in both host runtimes; the Linux address-book watcher is disabled and Windows resolution uses those pins without contacting the book. Optional payment/audit bindings are explicit, including zero for disabled services. Session factory and custody discovery entries are recorded for subsequent consumers but are not yet wired into all identity/custody paths. The production release must not be described as censorship resistant until those paths, custody and the full outage gates pass.

Capture current bindings and bytecode hashes with `node scripts/network/capture-contract-pins.mjs --book <address> --out <directory>` using agreeing fresh RPCs. Review every binding before activation; absent book entries do not prove that a legacy deployment does not exist.

After the ownership contract is deployed, prepare enrollment without a signing key using `node scripts/network/prepare-host-policy.mjs --policy <document.json> --owner <wallet> --registry <pin> --book <address> --out <new-directory>`. The supplied policy must explicitly choose its approval requirement and deny lists and bind the deployed ownership contract and exact host ID. The tool reads the active operator and accepted/pending owner through a fresh RPC quorum, refuses a different accepted owner or conflicting nomination, and writes the hash-named public policy plus ordered unsigned transactions. It resumes partial enrollment without repeating completed steps. Publish the document locally first, then re-read and simulate each transaction after its prerequisite confirms. Do not infer ownership from payout addresses or enroll an independent host into Enclave's wallet by default.

Build the shared runtime with `node scripts/build-host-admission.mjs`; `--check` verifies the committed bundle. Windows' import-closure deployment and the supervisor Dockerfile include that bundle so neither depends on a missing sibling npm installation.

## Required retirement evidence

- Independent operators and custodians selected and enrolled, with an independent quorum that can actually release.
- No required nan origin in artifact, policy, host-control, identity, DNS, certificate or custody paths.
- S3 writes, raw/CAR reads and all retained content survive loss of nan and one storage endpoint.
- Clean-host startup restores artifacts, secrets and persistent state while nan and the app owner are offline.
- New users authenticate, upload and deploy through the supported independent path.
- Wallet veto stops only its own host; independent hosting continues. Ownership transfer revokes the former wallet.
- Native ENS recovery works without enclave.host, and guest TLS renewal succeeds independently.
- A timed nan outage demonstrates these properties before services or data on nan are removed.

The proposed vault also pins its deployment ledger and SessionVault factory at construction; the compatible release reader uses that ledger and the pinned host registry. A real-chain test clears the book's ledger/registry entries and verifies that the independent custody quorum can still release. Older deployed vaults and readers retain their legacy authority path until explicitly migrated. Other serving and discovery paths still resolve mutable address-book entries; this custody change alone does not remove all global authority.

### Client catalog selection

Explicit versions obey platform moderation. Rejected, yanked and delisted releases
cannot be deployed; pending versions are available only through private development.
Public listings hide moderated releases while publishers and the catalog admin
retain their review/history views. The former All releases moderation bypass is
superseded. Host owners may add restrictions, never waive platform moderation.

### Public directory authority pins

Directories accept a complete `authorityPins` object naming `deployments`, `registry`, `connectivity` and `sessionVaultFactory`. The first two must be nonzero; zero explicitly disables either optional binding. A partial/invalid object refuses startup. With pins configured, lease/operator reads never consult the address book; unknown bindings refuse rather than falling back. Contract-owner and SessionVault policy signatures use fresh agreeing reads at the same confirmed block. EOA signatures remain checked against the deployment's verified owner.

Capture bindings and deployed bytecode hashes with `scripts/network/capture-network-authorities.mjs --book <address> --out <new-json-file>`. An explicitly verified legacy SessionVault factory can be supplied with `--session-factory` when the book entry is empty; a conflicting nonempty binding refuses. Review and copy the resulting `authorityPins` into directory configuration. This is deployed on all four public directories and all four providers; the cold-policy revision anchor remains unresolved. Route reads revalidate their snapshot when publication, policy or provider state changes during signature/chain verification. Bounded retries preserve replay floors and refuse a superseded withdrawal or policy; a concurrent accepted update no longer causes the old snapshot to omit a valid replacement.

### DNS route replicas

`DNS_READ_ONLY=1` runs the authoritative DNS responder against an explicit `ROUTE_MAP_URL`, without fleet discovery, signing keys or certificate challenge writes. It refuses a missing route-map setting and the box-control namespace. Co-locating it with a pinned public directory allows app-zone A answers to come from locally verified signed routes, with answer TTL bounded by each route's expiry. UDP and TCP, refusal of TXT mutations and expiry during directory failure are covered by tests. Raw TCP/IP-zone records are not yet supported by the signed directory response and must not be assumed migrated. This is a route-serving replica, not a certificate/namespace cutover: do not delegate production zones until independent DNS-01 issuance, control names, nameserver records and rollback have been prepared and verified. The production delegation and authenticated DNS-01 forwarding gates have now passed; raw IP/challenge queries use the migrated control authority while app routes use the local signed directory.

The provider entry point now accepts the same complete `authorityPins` object, including the connectivity binding used for paid service. Registry discovery and contract-owner signature checks use its chain quorum. The host privacy agent accepts these pins under `chain.authorityPins`; network policy verification uses that reader and rejects a conflicting legacy `enclaveNetwork.registry`. All four providers now run the pinned release, with unchanged WireGuard keys, restored peer counts, twelve routes and adapter health verified after each restart. The restarts caused brief control API interruptions. Host agents require a separate rollout with current process/status timestamps and end-to-end guest checks; cached readiness is insufficient. Build standalone artifacts with `node scripts/network/build-consumers.mjs OUTPUT_DIRECTORY`. The ESM bundles include a CommonJS compatibility wrapper for dependencies such as ws. Tests load the artifacts outside the repository without npm dependencies; also import-test the candidate using the target host's installed Node before replacing its running executable.

Four delegated DNS replicas are active on the existing provider IPv4 addresses, consuming only their local pinned directory. Public UDP/TCP queries for the adapter match verified routes. Standard certificate-verified HTTPS requests using those answers reach the ready guest and its 1,239-entry inventory. These replicas now serve production app/ip delegation, with challenge requests forwarded to minipc and tested over UDP/TCP.

### Consistent indexd recovery

`sudo scripts/storage/snapshot-indexd.sh NEW_PRIVATE_DIRECTORY` captures a quiesced PostgreSQL dump, consensus BoltDB, original configuration, exact deployed executable, optional GeoIP database and counts. It requires an active source, stops indexd, verifies its writer exited, and restarts the service before hashing the snapshot. Failure/signal cleanup attempts to restart the source. Treat the entire directory as sensitive; encrypt before transport, keep decryption material separately, and never print configuration or recovery phrases. This captures a recovery point, not a permanent write fence for cutover: the source resumes accepting writes.

A production capture stopped indexd for two seconds and resumed it. Its encrypted archive is hash-verified in root-only directories on all four providers without copying the decryption key. A network-disabled, port-free PostgreSQL 18.6 container restored the dump and started the exact deployed indexd binary with the consensus state and public GeoIP database on RAM filesystems. The recovered wallet binding loaded; scan and sync heights matched 597,924. Counts matched 1,302 objects, 530 slabs and 67 contracts, with no invalid indexes or unvalidated constraints. The temporary container and task-created plaintext source snapshot were removed after verification.

This does not verify remote slab reads, writes, a live target, wallet rotation or independent custody. For cutover, qualify target capacity, prepare TLS and DNS/endpoint access, fence the source writer and capture a final consistent state. Start only one network-connected indexd with that wallet. Once the new target accepts writes, restarting the old snapshot is not a safe rollback; stop the target and reconcile its latest state first. The existing recovery phrase exposure requires a controlled contract/wallet migration; replacing the seed in place is not supported. The live target, writer fencing, encrypted recovery and exact readback gates have passed. Wallet rotation and independent custody remain separate work.

### Portable qualification checker

The consumer builder also produces `checker.mjs`. `--directories-file PUBLIC_JSON_ARRAY` supplies explicit public directory origins without shell-specific JSON quoting; conflicting inline/file arguments and invalid origin arrays refuse startup. A migration package must include the existing WireGuard probe executable and use a protected local checker key. The nine qualification checks and 4 MiB integrity payload remain unchanged. Keep the checker separate from the providers it qualifies. Moving the existing key to another Enclave-operated host does not add an independent vote.

Checker handoff must be serialized. The provider deliberately replaces an earlier probe from the same checker identity and role. Parallel source/candidate probes can therefore interrupt each other, even if the candidate does not publish its verdict. Before stopping the source, verify sufficient remaining healthy signed-verdict coverage. Start the replacement only after the source stops; require a complete newly issued round on every directory and actual guest health. On failure, stop the destination before restarting the source. Do not accept cached status or old verdicts as migration evidence.

### Directory and DNS availability under load

Directory readers share only in-flight work, run at most four route checks concurrently and share provider verification within one immutable state snapshot. Every completed response rechecks publication, policy and provider context; affected routes retry and repeatedly changing routes are withheld. Replay floors and expiry remain enforced. A bounded loopback read allowance prevents public traffic from consuming all capacity needed by the local DNS consumer.

A deployment label without a current verified route now returns SERVFAIL rather than cacheable NODATA. Recursive resolvers can try another authority, while expired/unverified addresses remain unavailable. Explicit nameserver sets are served over both UDP and TCP.

### Direct-IP recovery ingress

Providers can opt into a loopback-only `noSniRoute` for a valid ClientHello without SNI. Unknown SNI and malformed TLS remain closed. The recovery Caddy front has a public IP certificate and serves only the configured recovery/control paths; arbitrary destinations are not accepted. Provider-local routes carry `api.enclavehost.eth` and `mcp.enclavehost.eth` to the migrated control TLS service. Public native metadata is implemented in `relay/native-discovery.mjs`; no application signing key or credential is exposed there.

### Attested release credentials after recovery

A copied root-owned `0600` signing seed is not readable by the relay's systemd
`DynamicUser`. This left the migrated relay answering `release_off` despite the
release switch and deployment allowlist being correct, and prevented EyesOff
from restarting. Preserve the seed's private source permissions. Install the
optional `relay/systemd/release-signing-credential.conf.example` drop-in and its
root-owned `0600` environment file as described in that example, then reload
systemd and restart the relay. Remove any inline `SECRETS_RELEASE_SIGNING_KEY`;
the release reader deliberately refuses simultaneous file and inline keys.

`LoadCredential` supplies the source to the service. `ExecStartPre` copies it to
a service-owned `0600` file inside a `0700` runtime directory, satisfying the
release reader's ownership and mode checks even when systemd's credential mount
uses group-read permissions. The source remains root-owned and is never placed
in an environment value. Do not chown it to a transient dynamic UID or make it
world-readable.

Recovery acceptance must exercise `/v1/secrets/release-status?id=<listed-id>`
(`listed: true`), the predictor's known-answer self-test, and a real attested
cold launch through public HTTPS and model inference. A healthy relay process,
existing warm guests, or a dashboard's `running` row alone cannot verify this
path. Preserve the deployment, measurement, lease and signing-key checks.

DNS failover applies to address queries (A, AAAA and ANY), not CAA/CNAME/TXT.
Without a serving route, CAA must still return the zone's authoritative NODATA
so the CA can consult the parent CAA policy. Returning SERVFAIL for CAA creates
a certificate/route startup cycle. Regression coverage exercises both UDP and
TCP for cold and expired route entries while retaining address fail-closed behavior.

Fence configuration updates as well as mutable state during a migration. The
source acquired admitted EyesOff release `58a0e7bd…` after the initial snapshot;
the target retained the prior list and could never reproduce the actual guest.
Compare the final running host's pinned release with the source's final release
and certificate admission sets, copy the exact manifest-pinned artifacts, and
verify every file before restoring that admission on the target. A release being
in the host's configuration alone is not evidence that the verifier migrated it.
